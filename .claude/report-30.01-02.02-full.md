# 30 января 2026 (четверг)

## Распознавание текста (OCR)

### Утро - Запуск OCR на томах

Начали распознавание текста на загруженных томах уголовного дела:
- **Том 001.pdf** - 332 страницы, большой файл ~214MB
- **Том 2.pdf** - 174 страницы, ~138MB
- **Том 3.pdf** - 167 страниц, ~120MB

### Проблема 1: OCR прерывается при обновлении страницы

При обновлении страницы браузера или случайном закрытии вкладки процесс OCR полностью останавливался. Приходилось запускать заново.

**Причина:** OCR работал через SSE (Server-Sent Events) - потоковое соединение между браузером и сервером. Закрытие браузера = разрыв соединения = остановка процесса.

### Проблема 2: Деньги списаны, результата нет

Особенно критично для Claude OCR - API списывает деньги за каждую обработанную страницу. Если на 50-й странице закрыть браузер - деньги за 50 страниц потеряны, результат не сохранён.

### Решение: Фоновый процесс OCR

Полностью переработана архитектура:

1. **Создан endpoint `/start-ocr-background`** - запускает OCR в отдельном потоке Python
2. **Процесс работает независимо от браузера** - можно закрыть вкладку, OCR продолжит работу
3. **Создана таблица `ocr_runs`** для хранения информации о каждом запуске:
   - ID запуска
   - Какой том обрабатывается
   - Какой движок (Tesseract/Claude)
   - Сколько страниц обработано
   - Статус (running/completed/failed)
   - Время начала и окончания

4. **Создана таблица `page_texts`** для хранения результатов:
   - Текст каждой страницы
   - Уровень уверенности распознавания
   - К какому OCR run относится

### Проблема 3: Импорт SessionLocal в фоновом потоке

При запуске фонового процесса возникала ошибка:
```
ModuleNotFoundError: No module named 'app.models'
```

**Причина:** Фоновый поток Python не имел доступа к контексту приложения.

**Решение:** Изменён импорт с `from app.models import SessionLocal` на `from app.models.database import SessionLocal` - прямой путь к модулю.

### Проблема 4: Статус OCR показывал неверные данные

На странице тома показывался статус "pending" хотя OCR уже шёл или был завершён.

**Причина:** Endpoint `/ocr-status` читал поле `volume.processing_status` которое не обновлялось.

**Решение:** Переписан endpoint - теперь проверяет активные записи в таблице `ocr_runs`:
- Если есть запись со статусом "running" - показывает прогресс
- Если последняя запись "completed" - показывает "готово"

### Добавлена возможность возобновления OCR

Создан endpoint `/resume-ocr`:
- Находит последний прерванный OCR run
- Определяет последнюю обработанную страницу
- Продолжает с неё, а не с начала
- Экономит деньги и время

### Добавлена история OCR

В интерфейсе добавлена вкладка "История" где видно:
- Все запуски OCR для тома
- Какой движок использовался
- Сколько страниц обработано
- Когда запущен и завершён
- Средняя уверенность распознавания

## Подготовка к векторизации

### Что такое векторизация

Для семантического поиска нужно:
1. Разбить текст на фрагменты (chunks) по ~1000 символов
2. Каждый фрагмент преобразовать в числовой вектор (embedding)
3. При поиске сравнивать вектор запроса с векторами всех фрагментов

### Создана таблица `text_chunks`

Структура:
- ID чанка
- К какому тому относится
- Номер страницы
- Текст фрагмента
- Позиция в тексте (начало-конец)
- Embedding (вектор в JSON формате)
- Какая модель создала embedding

### Создан endpoint `/vectorize`

Разбивает текст на чанки с перекрытием 200 символов (чтобы не терять контекст на границах).

# 1 февраля 2026 (суббота)

## Проблема с векторизацией - embeddings не создавались

### Обнаружение проблемы

Запустили векторизацию, endpoint вернул:
```
chunks_created: 433
embeddings_created: 0
```

Чанки создались, но embeddings = 0.

### Причина

В коде vectorize endpoint была функция `create_embedding()`, но она не вызывалась! Чанки сохранялись с `embedding = None`.

### Исправление

Добавлен вызов:
```python
embedding = create_embedding(chunk_text)
embedding_json = embedding_to_json(embedding) if embedding else None
```

## Проблема с локальной моделью - нехватка памяти

### Изначальный план

Использовать бесплатную локальную модель `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` для создания embeddings.

### Проблема

При попытке загрузить модель процесс зависал на несколько минут, потом падал.

**Причина:** На Mac всего 8GB RAM. Модель требует ~450MB, но с учётом PyTorch и других библиотек нужно больше. Свободной памяти было ~140MB.

### Что занимало память

Проверка показала:
- 3 терминала Claude Code: ~1.4GB суммарно
- Telegram: 126MB
- Chrome: ~280MB
- WhatsApp: 99MB
- Python сервер: 93MB

### Попытки решения

1. Закрытие лишних терминалов - не помогло достаточно
2. Ожидание загрузки модели - процесс висел 10+ минут
3. Модель скачивалась с HuggingFace, но не могла загрузиться в память

### Решение: Переход на OpenAI API

Переписан `embeddings_service.py`:
- Убрана локальная модель sentence-transformers
- Добавлена интеграция с OpenAI API
- Модель: `text-embedding-3-small`
- Стоимость: ~$0.02 за 1 миллион токенов (практически бесплатно)

Найден существующий OpenAI API ключ в проекте starec-bot:


Добавлен в `.env.local` проекта Starec-Advocat.

  - Фрагмент найденного текста
  - Релевантность в процентах

### Создан endpoint `/search`

Логика:
1. Получает запрос пользователя
2. Создаёт embedding запроса через OpenAI
3. Загружает все чанки с embeddings из базы
4. Вычисляет косинусное сходство между запросом и каждым чанком
5. Сортирует по убыванию сходства
6. Возвращает top_k результатов (по умолчанию 10)
